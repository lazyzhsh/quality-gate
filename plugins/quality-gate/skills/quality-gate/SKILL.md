---
name: quality-gate
description: Run configured L0-L5 quality gates before task completion; inspect claims, per-gate evidence, required domains, risks, and proposed exceptions.
---
1. Locate the installed plugin and the project root. Read `.quality-gate.json` before running; its command argv can execute project code.
2. For onboarding (no `.quality-gate.json`), run the `/quality-gate-init` guided dialogue: recommend a tier and template from the preset library (`node <plugin>/bin/qgate.mjs templates [lite|pro|max]`), confirm add-ons/disables and real commands with the user, then write config only through `node <plugin>/bin/qgate.mjs init <project-root> <answers-file>` — the CLI assembles and validates deterministically. Re-initialization (config deleted, leftovers present) lists leftovers via `qgate.mjs leftovers`, confirms deletion with the user, then uses `init --fresh`. For upgrading or incrementally adjusting an EXISTING config, run `/quality-gate-update` (`qgate.mjs inspect` → changes file → `qgate.mjs update`). Fallback when the dialogue is unavailable: adapt the example in `../../examples/demo/` to real project build/type/lint commands and actual claims. Do not replace existing configuration without reviewing it. Use `$NODE` to select this runtime; Windows npm.cmd should be invoked through a deliberately configured command processor or use node with npm-cli.js. Direct .cmd execution is not portable.
3. Invoke `node <plugin>/bin/qgate.mjs <project-root> close` (quote paths for the active shell), or use the requested edit/pr/release stage.
3b. Task-intent alignment (v1.17): at the start of a development task, run the `/quality-gate-intent` guided dialogue (goal → scope → acceptance → constraints, user confirms; register written only through `qgate.mjs intent <project-root> <answers-file> [--revise]`, never hand-edited). During the task, edits outside the registered scope FAIL `outside-task-scope` at close — fix by reverting the out-of-scope files or explicitly revising the intent (`--revise` with a reason; the CLI appends the revision chain and re-binds the acknowledged hash), never by hand-editing the register or the scope spec hash. `qgate.mjs intent <project-root>` alone renders the current baseline read-only. Soft forms (v1.17.1, register-activated): once a register exists, UserPromptSubmit injects the intent baseline line each prompt and PreToolUse warns softly on Write/Edit targets outside the scope (advisory, never intercepts — close drift reconciliation stays the authority); `intent.hooks:false` disables, `intent.capture:true` enables the unregistered-project guidance prompt.
4. Read the report. Explain failing checks and fix the underlying issue; re-run after edits. Never treat SKIP, ERROR, or an absent report as PASS. Repairs change the artifact, not the acceptance bar — disabling a gate, raising a threshold, adding an exemption, or rewriting an AC is an acceptance change that needs an explicit decision and its own record, never a default fix step.
5. Surface the result in your reply as Markdown body — never wrapped in a code fence, so bold and tables render — and keep surrounding prose to a sentence or two. On PASS paste the brief stderr line; on FAIL/ERROR paste the full Markdown table with per-gate durations, evidence sources, reasons and the 建议 column plus fix guidance, and after every fix-loop re-run show the updated report until PASS. Read the source column honestly: a run may mix 核验 (kernel-verified anchors), 声明 (runner self-report), and 降级 entries — mixed sources never mean everything was kernel-verified. Advisory convention hits render as a non-blocking line with counts; they keep the verdict but must be surfaced, not silenced. To show a past run without re-executing gates, use `node <plugin>/bin/qgate.mjs report <project-root> [runId]` (unique id prefix accepted; it re-renders the archived report and marks the original timestamp). Never end a turn with a bare verbal PASS/FAIL claim — the report block is the visible evidence for the user.
6. For persistence checks, adapt `../../examples/persistence-demo/` to an isolated test environment. The runner must call the API, wait for commit, independently query storage, and output the observation JSON. Never treat HTTP success or API response fields as persisted data. Do not run a write scenario against a production database by inference.
7. For ontology mapping, use `../../examples/fibo-demo/` as a format example. Check the selected provider and catalog SHA in evidence. FOUND means only that an exact IRI exists in the selected catalog; it does not prove the business field-to-concept mapping or OWL implications. The skeleton provider cannot pass this Gate.
8. Report status, evidence path, and remaining scope — concretely via the graded report block from step 5. Select only relevant configured gates; examples under `../../examples/` show L0–L5 protocols. Each result proves its configured inputs and runner observation, not untested project behavior. The full report also associates each claim with its gates (声明关联) and flags unverified claims (no gate executed) — linked gates passing does not prove the claim statement itself.
9. Stop hooks are feedback, with ZCode's three-round limit. Enforce commit/release policy using the same CLI exit code in CI. Exceptions are register-based, not verdict waivers: a proposed or expired exception blocks the run, and an approved unexpired one renders WAIVED — it only lifts the register blocking and never turns a FAIL gate into PASS. Registering an exception is an explicit acceptance decision, not a fix for a failing gate.
10. If the project sets `requiredLevels`, inspect `levelCoverage` and `unmetRequiredLevels` (protocol keys since v1.16; pre-1.16 archived runs still render via the `domainCoverage`/`unmetRequiredDomains` compatibility shim — never write those old keys into new configs or reports). A passing individual gate cannot compensate for a missing required level. Full format example: `../../examples/six-domain-demo/`; demo scanners and rollback drill must be replaced before production use.
