description: Guided config update for existing projects — inspect gates and template drift, apply incremental changes deterministically
---
Use the quality-gate skill. Run for projects that ALREADY have a `.quality-gate.json` (plugin upgrades, fixes, adding/removing gates, registry centralization). Resolve the installed plugin directory from ZCODE_PLUGIN_ROOT or the plugin source path shown by ZCode; never guess a directory. Quote paths for the active shell.

1. Inspect: run `node <plugin>/bin/qgate.mjs inspect <project-root>`. Report to the user: validity, gate list, per-stage budget usage, template provenance/match with drift (`templateGateIdsNotInConfig` / `configGateIdsNotInTemplate`), applicable add-ons, missing registry files, and the `suggestions` block (change-driven add-on recommendations from the uncommitted change surface — curated metadata, advisory only: present items with reason and matched file count when available; when unavailable say so honestly, never invent a basis). If the config is invalid, show the error and repair it first (hand fix with user review, or re-initialize via `/quality-gate-init --force --fresh` with explicit confirmation).
2. Ask by selection what to change (recommend from drift, missing registries, and the inspect `suggestions`): add add-ons (multiSelect from applicableAddOns — update accepts any catalog add-on; template tier scoping applies to init only; pre-select suggested items but let the user decide — you never write config on your own), disable gates (each needs explicit user confirmation; never to make checks pass), substitutions for real argv/cases/claims plus metrics `thresholds` (project metric names) and an `ontology` provider swap (fibo-pinned sha from `qgate.mjs templates` ontologyHint, or local-catalog) when relevant, `requiredLevels` adjustments, and whether to migrate root-level registry files into `.quality-gate/registries/` (`migrateRegistries`; existing targets are skipped and reported).
3. Write the changes file `{addOns?, disable?, substitutions?, requiredLevels?, ontology?, migrateRegistries?}` and run `node <plugin>/bin/qgate.mjs update <project-root> <changes-file>`. Unknown fields, gate-id collisions, unknown targets and unresolved placeholders are rejected without writing; on failure fix the changes file and rerun — never hand-edit `.quality-gate.json` to bypass. Disabling a gate that registry files still reference (testGateIds/verificationGateIds/affectsGateIds) surfaces as a `preflightGateRefs` warning — remap the registry or reconsider the disable.
4. Run `node <plugin>/bin/qgate.mjs <project-root> close` to verify. Newly added gates need their runners/registry files and fail closed until provided (CONFIG-GUIDE); never disable gates, fake evidence, or create exceptions to make close pass.
5. Report: what was added/disabled/substituted, migrated and skipped files, refreshed provenance timestamp, and the verification verdict with evidence path — pasting the graded close report into your reply as Markdown body, never inside a code fence (brief line on PASS; full table with durations, reasons and 建议 otherwise).
