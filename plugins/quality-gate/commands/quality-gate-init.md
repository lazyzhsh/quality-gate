---
description: Guided first-run onboarding — recommend tier/template, customize gates and real commands, initialize .quality-gate.json deterministically
argument-hint: "[--force] [--fresh]"
---
Use the quality-gate skill. Run for projects WITHOUT `.quality-gate.json` (with `--force` only after the user explicitly reviewed the existing file). Resolve the installed plugin directory from ZCODE_PLUGIN_ROOT or the plugin source path shown by ZCode; never guess a directory. Quote paths for the active shell.

1. Guard — three branches:
   a. `.quality-gate.json` EXISTS: do not overwrite. For upgrades, fixes or incremental changes run `/quality-gate-update` instead. Overwriting requires the user's explicit review of the existing config plus `--force`; a full reset additionally passes `--fresh`.
   b. Config MISSING but leftovers detected (`node <plugin>/bin/qgate.mjs leftovers <project-root>` reports registry files or a `.quality-gate/` directory): this is a re-initialization. Show the exact leftover list and ask the user to confirm deletion (deletion is irreversible, no backup). Only after confirmation continue the guided flow and pass `--fresh` at init. Do NOT treat leftover registries as inputs to analyze — re-initialization is a clean slate.
   c. Config missing, no leftovers: normal first run — continue.
2. Probe the project without executing project code: language, package manager, test/build/lint commands (read package.json, pyproject.toml, CI configs, README).
3. Ask by selection with the recommended option first: governance tier (lite/pro/max — see `node <plugin>/bin/qgate.mjs templates`), then a template within that tier (ids/domains from the same listing; recommend based on the probe).
4. Ask by selection: add-ons (multiSelect from the template's availableAddOns) and any template gates to disable — each disable needs explicit user confirmation and must never be used later to make checks pass.
5. Confirm per requiredSubstitutions entry (prefill from the probe): real argv for each runner gate (use `$NODE` for the Node runtime; Windows npm.cmd must run through a deliberately configured command processor or node with npm-cli.js — direct .cmd execution is not portable), behavior cases where required, and optionally claim statements, registry file paths (templates default registry files under `.quality-gate/registries/`) and metrics `thresholds` with the project's own metric names (six-domain's demo metrics are placeholders).
5b. If the chosen template carries an ontology block (six-domain's L2 semantic gates): ask for the provider. Recommend `{"type":"fibo-pinned","expectedCatalogSha256":"<from the ontologyHint printed by qgate.mjs templates>"}` (works out of the box with the shipped catalog) or `{"type":"local-catalog","file":"<project catalog>"}`; the default fibo-skeleton is a placeholder and semantic-profile will ERROR at close. Pass the choice as `ontology` in the answers — never hand-edit the config after init to switch providers.
6. Write the collected answers to a temporary answers file with contract `{templateId, addOns?, disable?, substitutions:{gates:{<id>:{argv|file|timeoutMs|cases|checks:{<checkId>:{argv|timeoutMs}}|thresholds}}, claims:{<id>:{statement}}}, requiredLevels?, ontology?}` and run `node <plugin>/bin/qgate.mjs init <project-root> <answers-file>` (append `--fresh` per step 1b, `--force` only per step 1a). The CLI assembles deterministically, validates, and refuses unresolved placeholders or an existing config; fix the answers and rerun — never hand-write or hand-edit the config to bypass.
7. The init output includes a registry preflight: existing registry files (requirements.json/release.json/decisions.json) whose `testGateIds`/`verificationGateIds`/`affectsGateIds` reference gate ids that no longer exist are reported as `preflightGateRefs` warnings. Remap those registry references to the new gate ids (or add the missing gates) BEFORE running close — do not disable gates to sidestep.
8. Run `node <plugin>/bin/qgate.mjs <project-root> close` for the first evidence run. Missing runners or registry files fail closed by design: report exactly which files/protocols to provide (CONFIG-GUIDE 引导初始化与模板库 and the 数据登记文件 tables). Fix inputs or add runners; never disable gates, fake evidence, or create exceptions to make close pass.
9. Report the outcome: template id and tier, add-ons/disables chosen, gates and claims written, files removed by `--fresh` (if any), preflight warnings (if any), first close verdict and the evidence report path — pasting the graded close report into your reply as Markdown body, never inside a code fence (brief line on PASS; full table with durations, reasons and 建议 otherwise).
