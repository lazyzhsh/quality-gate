---
Use the quality-gate skill. Run at the START of a development task, or whenever the user wants to revise the active intent (existing register → revision flow with `--revise`). Resolve the installed plugin directory from ZCODE_PLUGIN_ROOT or the plugin source path shown by ZCode; never guess a directory. Quote paths for the active shell.

Discipline: **问询不代写** — you propose, the user confirms; the register file is written ONLY through the CLI (`node <plugin>/bin/qgate.mjs intent <project-root> <answers-file> [--revise]`), never hand-written or hand-edited. The register's truth is whatever the user confirmed, not your summary of the conversation. Do not read back chat transcripts — `source` is a registration reference (e.g. `{kind:"user-prompt", ref:"任务首轮"}`), not a parsed quote.

1. Read current state first: `node <plugin>/bin/qgate.mjs intent <project-root>` (read-only render).
   a. No register: normal registration — continue.
   b. Register exists and the user asks to change scope/acceptance/constraints: revision flow — show the current baseline (taskId/statement/scope/revisions), ask what changed and why (reason is mandatory), then pass `--revise` with the full new answers (the CLI appends the revision chain with the previous content hash and re-binds `taskIntent.acknowledgedSha256` in every change-scope spec that declares it).
   c. Register exists and a NEW task is starting: tell the user the previous intent is still active — finish it (close PASS) or explicitly revise before starting fresh; never silently overwrite.
2. Ask in four confirmed steps (AskUserQuestion or equivalent; prefill from the task prompt, but the confirmed values are the register):
   ① 目标 statement — one sentence: what this task must deliver;
   ② scope — glob patterns for files this task is expected to touch (project-relative, `**` allowed; recommend based on the task, e.g. `src/payment/**`, `tests/payment/**`; scope may only narrow what the project's change-scope already allows);
   ③ acceptance — free-text criteria, or structured ones by adding `format:'gherkin'` (scenario + Given/When/Then or 假如/当/那么 steps; type from `@normal|@boundary|@negative|@exception|@state-transition` scenario tags, multiple scenarios allowed) or `format:'ears'` (one five-template sentence per line, EN or Chinese 当…时/在…期间/如果…则/其中…/应当); declared structures are kernel-validated at close (`ac-structure-invalid`/`ac-type-conflict` on mismatch) — free text without `format` is never structure-checked;
   ④ constraints — optional declarative constraints; the only kernel-judged one today is the literal `no-new-dependencies` (new dependency keys in package.json vs the change-scope base fail); anything else is recorded, not judged.
3. Ask who confirms (`confirmedBy`, e.g. the user id) — the confirmation trail is the only backing that the register matches the user's real intent; the framework does not judge semantics.
4. Write the collected answers to a temporary file with contract `{taskId, statement, scope: [globs], acceptance?: [{text, type?}], constraints?: [strings], source?: {kind, ref}, confirmedBy}` (+ `reason` when revising) and run `node <plugin>/bin/qgate.mjs intent <project-root> <answers-file> [--revise]`. The CLI structure-validates fail-closed, writes the register, and re-binds every change-scope spec that declares `taskIntent` — fix the answers and rerun on errors; never hand-edit the register or the spec hash.
5. If no change-scope gate declares `taskIntent` yet, tell the user drift reconciliation is inactive: adding `{"taskIntent": {"file": ".quality-gate/registries/task-intent.json", "acknowledgedSha256": "<from the CLI output>"}}` to the scope.json activates it (optionally `requireTaskIntent: true`); rerun the intent command afterwards to bind.
6. Report the outcome: taskId, content hash prefix, revisions count, rebound specs (or the inactive-binding note) — and remind: soft forms activate automatically once the register exists (UserPromptSubmit baseline line per prompt + PreToolUse advisory warning on out-of-scope Write/Edit; `intent.hooks:false` in .quality-gate.json disables them), and out-of-scope edits FAIL `outside-task-scope` at close; to widen scope legitimately, revise explicitly rather than editing files outside the register.
