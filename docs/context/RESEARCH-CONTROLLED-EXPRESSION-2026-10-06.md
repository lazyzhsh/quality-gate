# Quality Gate 受控表达应用方案

日期：2026-10-06。状态：设计提案，尚未实施运行时改动。

检查基线：本地提交 `ea03528`，产品版本 1.24.0。新增概念“受控表达”已登记于 [GLOSSARY](../GLOSSARY.md)。本方案对应 [RTM](../RTM.md) X12–X15，不将方案、文风检查或示例计作产品能力已实现。

## 1. 建议与目标

建议把受控表达用于三个位置：开发指令、项目文档、插件报告。解释性文字使用自然的短句；操作和判定使用固定结构；机器交换继续使用现有 JSON 协议。

本项目所需的“甜区”由用途决定，不按遵守多少条 STE 规则计分。硬约束放在状态、条件、范围和证据上。句长、词汇难度和语气主要作为写作建议。

预期改善的是四类工程问题：条件被漏读、术语被误解、建议诱导修改验收标准、结论超出证据范围。是否实际降低 Agent 错误率，需要实验验证。受控表达本身不能证明业务正确、阻止伪造观察，或替代权限控制。

第一轮复用现有能力，不新增 gate kind。优先修改会影响下一步行动的文案，再逐步增加可确定性检查的规则。

## 2. 来源与已有实验的证明边界

### 2.1 外部资料

- 已定位 [Karpathy 的原帖地址](https://x.com/karpathy/status/2105819303471976479)，本轮未能直接取得原帖正文。此前会话记录中的建议是以约 80% STE 风格改善输出可理解性。本方案不把“大幅解决对齐问题”归为已核实的原帖结论。
- [ASD 官方 FAQ](https://www.asd-ste100.org/STE_faq.html) 说明，STE 由写作规则和受控词典组成，通常限制一个词的词义和词性，并允许专业术语。短句、主动表达等原则可以借鉴到其他写作场景。
- [ASD 官方工具说明](https://asd-ste100.org/STEsoftware.html) 提醒，检查工具不能替代标准和作者审核。因此不将自建检查器或模型自述命名为“STE 合规认证”。

项目规则应使用自主编写的中文说明与英文示例。英文专业词采用本项目术语映射。中文不机械照搬英文单词数、词性限制或词典。第一轮不引入官方词典副本或外部语言服务。

## 4. 按用途确定约束强度

| 用途 | 推荐写法 | 必须保留的信息 | 检查方式 |
|---|---|---|---|
| README、PRD、设计解释 | 自然短句，先结论后理由，一段一个主题 | 目标、支持范围、局限及来源 | 人工审阅；句长和模糊用词仅提示 |
| AGENTS、commands、SKILL、操作步骤 | 一步一个主要动作；条件在动作前；明确执行者与停止条件 | 条件、主体、动作、对象、失败分支、验证方法 | 已登记引用与固定字段硬检查；语义完整性审阅 |
| AC、配置、runner 协议 | 固定结构和原有术语 | 类型、默认值、单位、允许范围、缺省/缺失语义、失败证据 | 现有 validate、Gherkin/EARS、CONFIG-GUIDE 检查 |
| CLI 摘要、Stop 反馈 | 从结构化结果按模板生成 | 判定、范围、来源、原因、下一步、证据位置 | 确定性渲染与反例测试 |
| 历史说明 | 可重写叙述和重组目录 | 当时版本、日期、状态、原始证据引用、修订说明 | 新旧事实逐项核对及链接检查 |
| 代码、路径、命令、日志、协议字面量 | 保持原样并与解释分开 | 可执行性与可复核性 | 专用语法/协议检查；不适用自然语言句长规则 |

不为了凑短句删除限定条件，不把“不知道”改成肯定句，不用正则表达式宣称已经理解全文。代码标识符遵循现有命名约定；不为文风再次迁移公共协议键。

## 5. 首版写作规则草案

以下编号用于方案讨论，尚未成为自动检查规则或配置项。

1. **固定术语。** 一个概念使用 GLOSSARY 中的名称。专业词第一次出现时解释，之后不为避免重复而换同义词。
2. **明确主体。** 区分内核、runner、adapter、Agent 和用户。例如写“内核核验输入哈希”，避免“系统进行了验证”。
3. **先写条件。** 用“如果 X，则 Y”。有多个分支时拆成表或编号步骤，明确所有条件同时满足还是任一满足。
4. **保持动作完整。** 步骤包含动作和对象。可执行规则须能定位输入和判断结果；“适当处理”“按需优化”不能单独充当验收条件。
5. **区分要求强度。** “必须/不得”表达要求或禁止；“建议”表达推荐；“可以”表达允许。描述当前实现和描述未来要求分别成句。
6. **区分事实、推断与建议。** 事实引用代码或证据；推断说明依据和未知项；建议不伪装成已完成行为。只在需要消歧的地方加标签，不要求每句都加标签。
7. **限定结论范围。** “通过”必须能够追到本次 stage、配置、输入和检查。声明关联了通过门禁，不等于声明全文已经得到证明。
8. **准确使用状态。** PASS、FAIL、ERROR、SKIP 保留原值。例外 WAIVED、Stop 允许收尾与门禁 PASS 分别表达。没有证据时写“未验证”或相应错误，不补造结果。
9. **先修复问题。** 失败建议先指出具体对象、观察差异与复验动作。修改范围、阈值、豁免或 AC 属于验收要求变更，不能默认作为修复动作。
10. **保证证据能定位。** 正文摘要给出本次报告路径与运行标识。旧报告注明原运行时间；复用结果注明未重跑。
11. **保留不确定性。** 缺失的来源、未知的覆盖面、未接入的工具明确标出。没有信号不等于低风险，也不等于高可信。
12. **优先可理解性。** 解释一段一个主题，步骤一个主要动作。英文句长和中文标点分句长度可作为提示，不设统一硬上限；参数、路径和引用不参与这种长度检查。

适合写入 AGENTS 的是简短核心规则和规范链接。细则集中在未来的 `docs/WRITING-GUIDE.md`。该文件本轮尚未创建；在实施第一批时建立，并由 GLOSSARY 管术语、WRITING-GUIDE 管表达，避免复制两份规则。

## 6. 插件报告设计

### 6.1 保留判定权边界

内核继续生成判定和证据。摘要层只从结果提取事实并选择文案。adapter 只描述宿主事件是否阻断。Agent 可以解释背景，但不能改写状态或证据范围。规则符合度不参与业务门禁的状态计算。

首批保持 stdout JSON、退出码和归档协议兼容，修改 stderr、Markdown、提示指令与测试。若后续确需新增结构化字段，应先定义缺省值、旧归档读取方式和版本规则，再同步 SPEC/CONFIG-GUIDE。不要把展示草稿直接当 runner 新入参。

### 6.2 两种展示长度，保留相同关键事实

- 简报：显示本次判定、stage、运行标识、通过/失败/错误/跳过计数、关键边界、完整证据入口。PASS 不隐藏降级、例外或未验证范围。
- 详情：按门禁或子检查给出对象、期望、观察、来源、原因、下一步。限制屏幕长度时显示省略项数和详情入口，不静默截去关键条件。

逐 Claim 视图按 `claimId` 关联门禁，显示关联结果、检查对象和未验证范围。关联了多少门禁可以确定性计算；自然语言声明是否被全部证明不能仅靠关联关系推断。

来源按实际观察细分：内核直接核验、runner 声明、原始输出交叉核验、显式降级、未提供。来源之间可能并存，不强行压成一个总等级。哈希一致只证明所比较内容一致，不证明来源独立或生产环境真实性。

### 6.3 失败报告示例

下表是假设场景的展示草稿，不是本轮执行结果；字段标签也不是新增机器协议。

| 项目 | 展示内容 |
|---|---|
| 判定 | FAIL：持久化检查未通过 |
| 范围 | 当前 close 配置中的退款场景 refund-01 |
| 原因 | 已观察的存储字段 `amount` 与期望值不同 |
| 期望 / 观察 | 100 / 90；单位为该场景约定的最小货币单位 |
| 来源 | 项目 runner 回报 API 调用与独立数据库回读；真实执行仍依赖 runner |
| 下一步 | 核对写入字段映射，修复后重跑同一场景 |
| 边界 | 此结果不验证其他退款场景或生产数据库 |
| 完整证据 | 实施时由本次归档报告路径填入，示例不伪造路径 |

### 6.4 必须覆盖的特殊状态

| 场景 | 预期表达 |
|---|---|
| 普通 PASS | 本次配置的检查通过；列出检查范围与未验证范围 |
| `new-only` 允许收尾 | 门禁报告仍为 FAIL。此次 Stop 未阻断；注明符合既有失败判定条件 |
| 复用归档 | 指明原运行时间与运行标识，说明输入核验后复用且未重跑 |
| 有效 approved Exception | 显示 WAIVED 及期限；说明关联门禁仍按自身状态判定 |
| 缺证据或 runner 异常 | 显示实际 ERROR/FAIL 和缺失对象，不能写“基本通过” |
| adapter 外层异常 | 明确此次宿主未阻断且不能据此判断质量；提示取得 CLI 判定 |
| advisory 命中 | 保留业务判定，同时显示建议项数、位置和详情入口 |

## 7. 开发指令与文档重构

### 7.1 开发流程

任务开始时，用现有任务意图登记明确目标、范围、AC 和约束；已有授权可直接落实，不因采用受控表达重复询问。缺少会改变实现选择的关键信息时才补充澄清。

实施前，将关键规则写成“条件—动作—可观察结果”。AC 复用已有 Gherkin/EARS 结构，不另造一套需求语法。结构校验只能证明结构符合要求；AC 是否覆盖用户意图和是否绑定真实用例仍需审查。

实施后，按已登记 AC 核对证据。修复只能改变实现；若实际需求需要变化，显式修订意图、规则或基线并留理由。不能通过修改检查标准来掩盖同一问题。

开发报告分别说明改动、验证、未验证范围。代码注释重点说明约束与选择理由；不把简单语句重复翻译成注释。

### 7.2 入口文档

- PROJECT-HANDOFF：保留当前版本、必读入口、运行方法、当前限制和下一步。旧版本逐行记录转为历史索引。
- PRD：保留问题、用户场景、目标/非目标、功能需求和路线。已完成版本流水记录链接到发行历史。
- RTM：继续作为实现状态的唯一索引。统一当前状态与验证日期，旧阶段结论保留在带日期的历史说明中。
- PLAN：只保留当前顺序、未完成项和明确不做。清理与当前交接矛盾的旧“下一步”。
- SPEC：每种 kind 按输入、前置条件、判定、失败证据、边界排列。
- CONFIG-GUIDE：保留完整选项表与可校验样例；新增“默认行为/缺失行为/条件关系”的清楚说明，不删掉为简洁而显得冗长的兼容性规则。

用户已允许历史文档重构和重写，可按主题重新组织说明。重写应保留日期、版本、原始结果、证据引用与原稿可追溯关系。原始日志和报告保留原样；不能把过去的 SKIP 改成 PASS，或把 CLI 验证写成实机验收。移动文件后检查全仓库相对链接。

### 7.3 改写样本：Stop 边界

以下为建议写法，事实依据为 `freshness.mjs`、`hooks/adapter.mjs` 和内核报告协议：

1. Stop 只在报告和输入满足复用检查时使用旧判定。
2. 复用检查比较输入内容摘要。仅保持修改时间不能保证复用。
3. 仅允许清单内的确定性文件检查复用。外部 runner 检查需要重跑。
4. `stop.blockMode=new-only` 可以允许符合条件的既有失败结束本次 Stop。报告仍为 FAIL。
5. adapter 外层异常只发出非阻断消息。这个消息不能作为质量 PASS。
6. 交付准出必须检查 CLI 退出码，不能只观察宿主是否允许结束。

各项指向一个可核对事实。实现时应在更详细的规则表中保留复用条件全集；本段不替代该条件表。

## 8. 自动检查怎样接入

先使用 `convention-alignment` 的现有 `banned-words` 与 `argv`。后者可调用零依赖的本地文档检查脚本。脚本只报告发现，门禁按规则严重度判定。使用已有 `severity: advisory` 做首轮观察，不引入默认联网或模型裁判。

| 规则 | 首轮处理 | 理由及边界 |
|---|---|---|
| 已登记弃用词、引用失效 | 可确定命中的规则阻断 | 沿用现有边界；引用存在不证明引用内容正确 |
| 新版指引引用已退役字段 | 在已登记字段位置阻断 | 迁移说明、代码和旧归档兼容样例必须区分，不能全仓库字符串封禁 |
| 固定报告中的状态、数字、证据引用不一致 | 渲染器测试阻断 | 检查结构化数据与输出一致性，不用语言模型猜测 |
| 关键规则文档缺少声明的必需段落 | 在已采用固定模板的文件中阻断 | 只能证明段落存在，不能证明论证成立 |
| 长句、模糊词、一个步骤含多个动作 | advisory | 中文分句和技术句型存在误报，不直接判质量失败 |
| “全部完成”等超范围结论 | 固定报告由模板限制；自由文本先提示 | 仅靠正则不能判断所有上下文；引用和负例不能误报为作者结论 |

实施时先识别 Markdown 正文、表格、代码块、行内字面量、引用和历史区块，分别处理。不能简单跳过全部表格，因为 RTM 与配置选项就在表格中。

新增内部规则需有编号、来源位置、扫描范围、正例、反例、漏检边界和豁免记录。若这些内容成为可配置字段，同一提交必须更新 CONFIG-GUIDE 的选项表、jsonc 样例、validate 与摘要提取测试；本轮不预设新的配置协议。

扫描零文件必须可见，不得作为“所有文档符合规范”的证据。检查脚本自身失败应为 ERROR。不能吞掉错误后回报空 findings。为避免自引用误报，规则样例和测试夹具需要明确范围，但范围不能因此漏掉真实产品输出。

有确定性能力、扫描范围清楚且误报已核实的规则才升级为阻断。句长分数、所谓“80% 合规分数”不作为发布门禁。

## 9. 实施顺序与验收

| 批次 | 变更 | 验收条件 |
|---|---|---|
| 1：纠正文案与指令 | 修复旧字段/例外表述；移除默认降低检查要求的建议；建立 WRITING-GUIDE；AGENTS 与插件指令引用核心规则 | 状态、退出码与检查范围不变；特殊状态示例逐项核对；正反例和全量回归通过 |
| 2：报告表达 | 逐检查来源、逐 Claim 范围、advisory 可见性、旧报告与复用说明 | 混合来源不能显示为全部已核验；FAIL/ERROR/SKIP 不被展示成 PASS；归档读取兼容；受影响 demo 与全量回归通过 |
| 3：文档重构及检查 | 重写当前入口与高频规范；连接确定性检查；历史叙述整理 | 事实核对表无遗漏；代码/JSON 样例仍可运行；链接有效；扫描覆盖面明确；误报样例有解释 |
| 4：效果实验 | 比较读者理解和 Agent 修复行为 | 记录真实错误率与耗时，区分改善、无差异和退化；据数据调整软规则 |

第二批与当前 PLAN 中的“逐 Claim 证明范围、混合来源显示”合并，不作为平行重复功能。若某项需要新增采集协议，拆成独立增量，不为一次文案改造扩张全部内核。

实现期间按 AGENTS 运行全量回归 `node devtools/run-suite.mjs plugins/quality-gate/tests/*.test.mjs` 和受影响 demo。若改变打包/安装结构，运行 `python devtools/build_delivery.py` 并复验解包。每批同步 RTM、SPEC、发布说明和验证证据；增加配置时同步 CONFIG-GUIDE。

客户端验证另记：从源码构建，先同步 marketplace 快照，再执行客户端插件行“更新”，用文件系统核验版本、SHA 和 Stop 报告。CLI 与模拟通过不替代 ZCode 实机验收。

## 10. 如何证明方法有效

### 10.1 确定性验收先行

建立事实与输出的反例集，至少覆盖：PASS 夹带 SKIP、ERROR、缺报告、混合来源、缺来源、有效/过期例外、new-only 允许收尾、复用旧报告、advisory、摘要截断、AC 结构错误。对同一输入比较新旧门禁判定与退出码，表达改造不应改变它们。

专测下一步建议：结构错误应指向结构修复；业务失败不能默认指向禁用 Gate、降低阈值或新增豁免。需要改变验收要求的场景单列，验证是否明确呈现该变更。

### 10.2 Agent 行为对照

使用四组区分语言与结构各自的效果：现有表达、仅改写语言、仅增加明确结构与证据边界、语言与结构组合。严格 STE 作为少量写作附加对照，不要求中文模拟英文词典。

第一轮可选 12 个代表场景，每组每场景重复 3 次，共 144 次独立任务；这是实验设计数量，尚未执行。场景包括既有失败、输入内容变化、缺原始输出、例外、AC 修复、混合来源等。

固定代码基线、工具可用性、模型版本和推理设置。每次使用新上下文，随机分配组别。各组保留相同的必要事实与任务难度，避免组合组因额外获得答案而虚增效果。试验前确定评分规则，留出未用于修改规则的场景。

主要指标：错误宣称 PASS、未经授权修改验收要求、遗漏条件、错误下一步动作。辅助指标：修复轮数、用时、token 和文本长度。将模型版本、原始输出、工具轨迹和实际结果一起留档，报告次数、分母与不确定性；同一场景多次采样不等于同等数量的独立业务场景。

人类理解另做盲测，记录答对条件题的比例、定位证据时间和信心。高信心答错尤其值得关注。不能只让生成答案的模型给自己打分，也不能以句长下降替代行为结果。

### 10.3 成功与失败的表达

可以报告“在这些任务与模型设置下，错误动作由 X/N 变为 Y/N”。没有足够差异时报告“尚未观察到改善”。任何结果都不直接推导为通用对齐问题已解决。
